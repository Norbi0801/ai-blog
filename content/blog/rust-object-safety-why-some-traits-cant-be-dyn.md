You write a perfectly reasonable trait. You try to use it as `dyn Trait`. The compiler hits you with `error[E0038]: the trait Foo cannot be made into an object`. If you've spent any time in Rust, you've seen it. The fix is sometimes obvious and sometimes deeply unobvious. This post is the long version of "why" - what the rules actually mean, what the vtable can and can't represent, and how popular crates work around the limits.

If you haven't read [trait objects vs enums vs generics](/blog/trait-objects-vs-enums-vs-generics-picking-the-right-polymorphism-in-rust/), start there - I covered the basic vtable layout and the rule list at the surface level. This post goes one layer down.

## A naming note: object safety is now "dyn compatibility"

Rust 1.83 [renamed](https://blog.rust-lang.org/2024/11/28/Rust-1.83.0/) the concept from "object safety" to "dyn compatibility." The compiler error message changed from "the trait X is not object safe" to "the trait X is not dyn compatible." The rules are identical - the new name just describes what the property actually means. Searches, blog posts, and rustc errors before late 2024 use the old term. I'll use both interchangeably.

## What the vtable actually contains

A `&dyn Trait` is a fat pointer: a data pointer to the value, and a vtable pointer to a static table generated by the compiler. The vtable for any `(Type, Trait)` pair has a fixed shape:

```
Vtable for (Circle, Shape):
  ┌──────────────────────────┐
  │ drop_in_place: fn(*mut)  │  destructor
  │ size_of: usize           │  size of Circle
  │ align_of: usize          │  alignment of Circle
  │ method_1: fn(...)        │  Shape::area
  │ method_2: fn(...)        │  Shape::name
  │ ...                      │
  └──────────────────────────┘
```

The first three fields are always there - they're how `Box<dyn Trait>` knows how to free itself, how `mem::size_of_val(&dyn_value)` works, etc. After that, one function pointer per trait method, in declaration order. You can see the actual layout the compiler uses in the [`rustc_codegen_ssa::meth`](https://github.com/rust-lang/rust/blob/master/compiler/rustc_codegen_ssa/src/meth.rs) module.

Three properties of this layout drive every dyn-compatibility rule:

1. **The vtable is one-per-(Type, Trait), generated at compile time.** The compiler must know every entry it needs to write into it, statically.
2. **Each entry is a single function pointer with a single signature.** No overloading, no specialization at the vtable level.
3. **The data pointer is opaque.** The caller has 8 bytes pointing at "something" - the compiler can't read its layout, only call methods through the vtable.

Every rule below is a consequence of one of these three.

## Rule 1: no Self in return position

```rust
trait Cloneable {
    fn clone_self(&self) -> Self;
}
```

`Self` is `Circle` for `impl Cloneable for Circle` and `Rectangle` for `impl Cloneable for Rectangle`. They have different sizes (8 vs 16 bytes), different alignments, possibly different drop semantics. A function pointer in the vtable has *one* signature. There's no calling convention that says "return something that's 8 bytes for callers holding a Circle and 16 bytes for callers holding a Rectangle."

This is why [`Clone`](https://doc.rust-lang.org/std/clone/trait.Clone.html) is not dyn-compatible. Its definition is essentially:

```rust
pub trait Clone: Sized {
    fn clone(&self) -> Self;
}
```

Two strikes against dyn: returns `Self`, and requires `Self: Sized`. You can't write `&dyn Clone`.

### Workaround A: return a boxed trait object

```rust
trait DynClone {
    fn clone_box(&self) -> Box<dyn DynClone>;
}

impl<T: Clone + 'static> DynClone for T {
    fn clone_box(&self) -> Box<dyn DynClone> {
        Box::new(self.clone())
    }
}
```

`Box<dyn DynClone>` has a known size (a fat pointer, 16 bytes). Now the vtable entry has a fixed return type. The blanket `impl<T: Clone>` means any `Clone` type automatically gets a `DynClone` impl. This is the pattern the [`dyn-clone`](https://crates.io/crates/dyn-clone) crate generalizes. Its [source](https://github.com/dtolnay/dyn-clone/blob/master/src/lib.rs) is worth reading - 200 lines of well-commented code that solves "I need to clone things behind dyn."

You can then implement `Clone` for the wrapper:

```rust
impl Clone for Box<dyn DynClone> {
    fn clone(&self) -> Self {
        self.clone_box()
    }
}
```

Now `Box<dyn DynClone>` itself is `Clone`. The fat pointer gets duplicated, and `clone_box` allocates a fresh heap copy of the underlying value.

### Workaround B: where Self: Sized to exclude from vtable

```rust
trait Mixed {
    fn area(&self) -> f64;                          // in vtable
    fn copy(&self) -> Self where Self: Sized;       // NOT in vtable
}
```

The `where Self: Sized` clause tells the compiler "this method is only callable when `Self` is a concrete sized type." For `dyn Mixed`, where `Self` is the unsized `dyn Mixed` itself, the method is invisible. The vtable contains only `area`. This pattern lets you keep `Self`-returning helpers on the trait while preserving dyn compatibility.

You can see this exact technique in [`std::iter::Iterator`](https://doc.rust-lang.org/std/iter/trait.Iterator.html). `Iterator::next` is dyn-compatible. `Iterator::map`, `Iterator::filter`, `Iterator::collect` all have `where Self: Sized` (directly or transitively through generic bounds). `dyn Iterator<Item = i32>` works for calling `.next()`. You can't call `.map()` on it.

## Rule 2: no generic type parameters on methods

```rust
trait Logger {
    fn log<T: Display>(&self, value: T);
}
```

A vtable has a finite number of slots, written by the compiler before the program runs. `log::<i32>`, `log::<String>`, `log::<MyType>` are different monomorphized functions. There's no way to write all of them into one vtable, because the compiler doesn't know which `T`s you'll call it with.

### Workaround: take a trait object as a parameter

```rust
trait Logger {
    fn log(&self, value: &dyn Display);
}
```

Now there's exactly one signature. The polymorphism moves *inside* the call - `value: &dyn Display` is itself a fat pointer with its own vtable. You pay for two vtable lookups instead of one (your method, then `Display::fmt`), but the trait is dyn-compatible.

This is why [`std::io::Write`](https://doc.rust-lang.org/std/io/trait.Write.html) has both `write` (takes `&[u8]`, dyn-compatible) and `write_fmt` (takes `fmt::Arguments`, also dyn-compatible). It deliberately avoids generic methods.

### When the generic returns a wrapper

A common pattern that breaks: builders that consume a generic to produce a transformed type.

```rust
trait Pipeline {
    fn then<F: Fn(i32) -> i32>(self, f: F) -> ChainedPipeline<Self, F>;
}
```

This has both problems: a generic method, and a return type that depends on `Self` and `F`. The fix is to erase the closure as a `Box<dyn Fn>`:

```rust
trait Pipeline {
    fn then(self: Box<Self>, f: Box<dyn Fn(i32) -> i32>) -> Box<dyn Pipeline>;
}
```

You lose the inlining benefit of generic closures but gain dyn compatibility. Whether that trade is worth it depends on the call frequency.

## The erased trait pattern (erased-serde)

The most elegant escape hatch for "I need dyn but my trait has generic methods" is the *erased trait* pattern. [`serde`](https://serde.rs)'s `Serialize` trait is famously not dyn-compatible because it uses generics everywhere:

```rust
pub trait Serialize {
    fn serialize<S: Serializer>(&self, serializer: S) -> Result<S::Ok, S::Error>;
}
```

`<S: Serializer>` - a generic method. Doomed for dyn. Yet plenty of code wants `Vec<Box<dyn Serialize>>`. The solution is [`erased-serde`](https://crates.io/crates/erased-serde), which defines a parallel trait that's structurally identical but uses trait objects instead of generics:

```rust
pub trait Serialize {
    fn erased_serialize(&self, serializer: &mut dyn Serializer)
        -> Result<(), erased_serde::Error>;
}
```

The trick: `erased_serde::Serializer` is a dyn-compatible mirror of `serde::Serializer`. Each method takes concrete types or other trait objects, never generics. A blanket impl bridges them:

```rust
impl<T: serde::Serialize + ?Sized> erased_serde::Serialize for T {
    fn erased_serialize(&self, s: &mut dyn erased_serde::Serializer)
        -> Result<(), erased_serde::Error>
    {
        // delegate to the real serde::Serialize
        ...
    }
}
```

Now `Box<dyn erased_serde::Serialize>` works. You pay two vtable hops per method call instead of monomorphization, but you can store heterogeneous serializable values. The [actual implementation](https://github.com/dtolnay/erased-serde/blob/master/src/ser.rs) in dtolnay's repo is 800 lines of carefully managed lifetimes and unsafe code, but the *concept* is just "wrap generic methods in a dyn-friendly facade."

You can apply this pattern to your own traits whenever you have a generic-method API that some users need to use behind `dyn`. Define a parallel `Erased` trait, blanket-impl from the original, and document that users should put `Box<dyn ErasedFoo>` in collections, not `Box<dyn Foo>`.

## Rule 3: no associated constants

```rust
trait Bounded {
    const MAX: usize;
    fn value(&self) -> usize;
}
```

A vtable holds function pointers. Constants aren't function pointers. Different implementors define different `MAX` values, and the vtable has no slot to store a `usize` per type.

The fix is trivial: turn the constant into a method:

```rust
trait Bounded {
    fn max(&self) -> usize;
    fn value(&self) -> usize;
}
```

Now `max` gets a vtable slot. The optimizer will probably fold the call to a constant load anyway. You spend one extra cycle per access.

## Rule 4: no static methods (no self receiver)

```rust
trait Constructor {
    fn new() -> Self;
}
```

A vtable lookup needs an object to start from - the data pointer + vtable pointer pair. `new()` has no receiver. There's no `&self` to derive a vtable from. Even if you could find the vtable somehow, `Self` in the return position has the same problem as Rule 1.

The standard fix is `where Self: Sized`:

```rust
trait Constructor {
    fn new() -> Self where Self: Sized;
    fn name(&self) -> &str;  // dyn-callable
}
```

You can still write `dyn Constructor`. You just can't call `<dyn Constructor>::new()` - which makes sense, because what type would you construct?

## Rule 5: no Self in supertrait type parameters

```rust
trait Comparable: PartialEq<Self> {
    fn label(&self) -> &str;
}
```

`PartialEq<Self>` expands to `eq(&self, other: &Self) -> bool`. The vtable would need a method that takes another `&Self`. But `Self` for `dyn Comparable` is the unsized `dyn Comparable` - and you'd be comparing across concrete types. What does `circle.eq(&rectangle)` even mean?

This is a deep limit. There's no general workaround that preserves the original semantics - if you genuinely need to compare two `dyn` values, you typically downcast through `Any`:

```rust
use std::any::Any;

trait Comparable: Any {
    fn as_any(&self) -> &dyn Any;
    fn equals(&self, other: &dyn Comparable) -> bool;
}

impl<T: PartialEq + Any> Comparable for T {
    fn as_any(&self) -> &dyn Any { self }
    fn equals(&self, other: &dyn Comparable) -> bool {
        other.as_any().downcast_ref::<T>().map_or(false, |o| self == o)
    }
}
```

`other` arrives as `&dyn Comparable` (pointer-sized, unambiguous). The implementation downcasts to the concrete `T`. If the types differ, equality is false. If they match, normal `PartialEq` runs. This is essentially how [`dyn-eq`](https://crates.io/crates/dyn-eq) and similar crates work.

## async fn in traits and dyn

Rust 1.75 stabilized [`async fn` in traits](https://blog.rust-lang.org/2023/12/21/async-fn-rpit-in-traits/) (and return-position `impl Trait`). But:

```rust
trait Fetcher {
    async fn fetch(&self, url: &str) -> Vec<u8>;
    // desugars to: fn fetch(&self, url: &str) -> impl Future<Output = Vec<u8>>;
}
```

`impl Future` is an unnamed, possibly-different type per implementor. It's effectively `Self`-shaped from the vtable's perspective - different size per impl. So this trait isn't dyn-compatible by default. The compiler will tell you to either return a `Pin<Box<dyn Future>>` manually, or use the [`async-trait`](https://crates.io/crates/async-trait) crate, which rewrites all your `async fn`s into methods returning `Pin<Box<dyn Future + Send>>`. That's the same workaround as Rule 1: erase the unknown-size return into a fat pointer.

The newer alternative is [`trait-variant`](https://crates.io/crates/trait-variant), which generates *both* a generic version (for static dispatch) and a dyn-compatible version with boxed futures. You pick which to use at the call site.

## Splitting traits: the dyn-compatible core pattern

When a trait has both dyn-incompatible features (constructors, generic helpers) and a dyn-compatible core, split it:

```rust
trait ShapeCore {
    fn area(&self) -> f64;
    fn name(&self) -> &str;
}

trait Shape: ShapeCore + Sized {
    fn new(args: f64) -> Self;
    fn scale<F: Into<f64>>(&self, factor: F) -> Self;
}
```

`ShapeCore` is dyn-compatible: only `&self` methods returning concrete types. `Shape` extends it with constructors and generics, requiring `Sized`. Code that needs heterogeneous collections uses `Box<dyn ShapeCore>`. Code that's generic over a known concrete type uses `T: Shape`.

This is exactly the structure the standard library uses for [`Read`](https://doc.rust-lang.org/std/io/trait.Read.html) - the core methods (`read`, `read_to_end`) are dyn-compatible, and the convenience methods that take generics (`read_to_string` with `Buf` types, etc.) are gated through `where Self: Sized` or live on the [`BufRead`](https://doc.rust-lang.org/std/io/trait.BufRead.html) extension trait.

## Diagnosing dyn-compatibility errors

E0038 errors print a list of *which rule* you violated. Read it:

```
error[E0038]: the trait `Cloneable` cannot be made into an object
  --> src/main.rs:5:13
   |
5  |     let _: &dyn Cloneable = &Circle { r: 1.0 };
   |             ^^^^^^^^^^^^^ `Cloneable` cannot be made into an object
   |
note: for a trait to be "object safe" it needs to allow building a vtable to allow the call to be resolvable dynamically; for more information visit
      <https://doc.rust-lang.org/reference/items/traits.html#object-safety>
note: the trait cannot be made into an object because method `clone_self` references the `Self` type in its return type
```

The error tells you the exact violation. Fixes follow a small menu:

1. *Method returns Self* -> add `where Self: Sized` if dyn shouldn't call it, or return `Box<dyn Trait>`.
2. *Generic method* -> replace with `&dyn Trait` parameter, or split trait, or use erased-* pattern.
3. *Associated constant* -> convert to a method.
4. *Static method (no receiver)* -> add `where Self: Sized`.
5. *Self in supertrait* -> use the `Any` + downcast pattern.
6. *Async fn / RPIT* -> use `async-trait` or `trait-variant`.

## Why the rules exist as a checklist, not a smarter compiler

People sometimes ask: why doesn't the compiler infer dyn compatibility automatically, or generate a fatter vtable when needed? The answer is partly historical (the rules predate a lot of Rust's type machinery) and partly fundamental. A vtable that handles `fn clone(&self) -> Self` would need to either:

- Allocate the result on the heap and return a pointer (which is what the workaround does explicitly).
- Pass a writeback pointer for variable-size returns (think C's hidden return pointer for large structs, but with runtime-discovered sizes).

Both are doable but ugly. Rust chose the "explicit and obvious" route - if you want runtime polymorphism, you pay for it visibly with `Box<dyn Trait>`. The vtable stays a simple, predictable structure. Tradeoffs of this kind are why the Rustonomicon's [chapter on coercions](https://doc.rust-lang.org/nomicon/coercions.html) and the [reference's trait section](https://doc.rust-lang.org/reference/items/traits.html#object-safety) read more like a contract than a black box.

## Summary

The dyn-compatibility rules look like an arbitrary list. They aren't. They're a direct consequence of how the vtable works: a static, fixed-size table of function pointers with one signature each, accessed through an opaque data pointer. Anything that breaks one of those properties - unknown-size returns, infinite method instantiations, non-function entries - can't fit.

The workarounds all do the same thing: hide the troublesome part behind a sized indirection (`Box<dyn>`), or move it out of the vtable (`where Self: Sized`), or write a parallel dyn-friendly facade (the erased-* pattern). When you hit E0038, identify which rule you broke and pick the matching fix. Five rules, five tools. The compiler tells you which.
